# Windows security verification — 0.8.0-beta.3

Date: 29 October 2026. Target: Windows 10/11 x64. This is local developer-PC evidence, not a clean-device certification or a penetration test.

## Completed checks

- All 97 source tests passed, including real media processing and regression cases for engine tampering, changed-file cache invalidation, junctions, untrusted executable paths, proxy authentication, excessive thumbnail dimensions, diagnostic privacy and signed release metadata.
- npm audit reported zero known npm vulnerabilities across 320 dependencies. This does not cover every native engine or unpublished flaw.
- All 40 existing packaged checks passed: beta workflow 14, media details 6, IPC 3, experience 9 and reliability 8.
- Five packaged security checks passed: production fuse states; matching native ASAR integrity resource; ignored Node environment injection with successful renderer IPC; modified bundled FFprobe rejected; modified ASAR code rejected before successful application IPC. The test mutates an isolated copy only.
- Live YouTube playlist preview passed. A public direct MP4 was inspected, downloaded through the authenticated proxy and verified with FFprobe.
- The high-confidence secret scanner passed. CodeQL, Dependabot and GitHub workflow configuration are prepared locally; their remote execution and private reporting setup remain publication tasks.

## Performance

The local warm-cache benchmark hashed 328,136,200 bytes across four engines in 970 ms. Twenty-five subsequent toolchain checks averaged 2.44 ms each and did not increase the four full-hash operations. Real startup time varies with disk, antivirus, device and cache state. No additional network request is needed for engine integrity checking.

## Packaging and installation

Installer and portable executables were built with ASAR integrity enforcement, ASAR-only loading and disabled RunAsNode/NODE_OPTIONS/CLI inspection. Source modules in the packaged archive match the working source. Final native hashes, release assets and detailed reports are generated by `scripts/prepare-release.mjs` after all current packaged reports are present.

The per-user upgrade completed successfully. All five backed-up profile files remained byte-identical. The installed executable and app.asar match the tested package, all four bundled engines match the trusted manifest, production fuses are enabled as intended, and three installed renderer/preload IPC checks passed in an isolated test profile. Startup performed four full engine hashes. Results are in `artifacts/installed-security-upgrade.json`. No media files were deleted by this upgrade.

## Remaining gates and observations

- The beta remains unsigned. A trusted Authenticode certificate/service is not configured.
- The maintainer Ed25519 key list is empty. Desktop release discovery fails closed; no fake identity or private release key was generated. Official engine repair still uses publisher HTTPS/checksums. See SIGNING.md for provisioning and its separate trust boundaries.
- Some first packaged runs timed out while other test instances were running; subsequent runs passed. Keep startup/low-resource behavior in beta validation rather than claiming a timing guarantee.
- Test on a separate clean Windows account/device, verify GitHub security workflows after publication, configure private vulnerability reporting and complete dependency redistribution/source review before a broad public release.
- Native media tools are not in the renderer sandbox. These controls reduce risk; they do not protect an already-compromised Windows user account or guarantee all media is harmless.
